# Phase 4 Plan

基于当前已有 UI 基础、manifest 和部署脚本，但仍缺少发布硬化与生产交付收尾的状态整理。

## 当前状态

- UI 已具备统一视觉系统和移动端底部导航，说明响应式基础已经存在。
- `public/manifest.json` 已存在，说明 PWA 的最基础元数据已经就位。
- `package.json` 已有 `deploy` 脚本，`wrangler.jsonc` 已配置 D1 绑定，说明 Cloudflare 发布路径已初步建立。
- 当前仍缺少上线前常见的“可安装性、离线策略、发布验收、运维回退”收尾动作。

## 本阶段目标

把应用从“本地可跑、结构完整”推进到“线上可部署、可安装、可观测、可回退”的生产可交付状态。

## 剩余任务

### 1. 完成跨页面体验收尾

- 为上传、发票、分析、比价、供应商页面统一 loading、empty、error 状态。
- 检查移动端和桌面端关键断点，修正表格、导航和长文本的可用性问题。
- 审核现有动效，保留必要的页面进入和状态切换反馈，避免装饰性动画影响效率。
- 完成标准：主流程在桌面和手机尺寸下都能稳定使用。

### 2. 补齐 PWA 能力

- 审核 manifest 字段，确认名称、图标、主题色、启动入口满足安装要求。
- 明确离线策略，至少提供离线提示页或最近一次可读内容的降级方案。
- 如产品目标需要，补 service worker、安装提示和缓存更新策略。
- 完成标准：应用可被安装，并且断网时行为可预期。

### 3. 固化 Cloudflare 发布流程

- 整理本地、预发、生产环境的配置约定，包括 D1、环境变量和密钥来源。
- 明确远端 migration 执行顺序，避免先部署代码后缺表，或先迁移后代码不兼容。
- 形成一键或标准化发布步骤，减少手工失误。
- 完成标准：团队成员可按同一套步骤完成部署。

### 4. 增加可观测性与回退方案

- 增加全局错误边界、关键服务端日志和失败提示。
- 规划数据库备份、导出或回退策略，至少保证生产数据变更前有恢复手段。
- 定义上线后首周需要重点关注的指标，例如导入失败率、查询错误率、慢查询数量。
- 完成标准：发布后出现问题时，能够定位、缓解并回退。

### 5. 做上线验收

- 对生产环境执行端到端 smoke test，覆盖导入、列表、详情、分析、比价主路径。
- 在真实设备上验证安装体验、图标、启动页和导航操作。
- 复核 `README` 与部署说明，使新成员能从零完成构建和发布。
- 完成标准：上线验收有明确记录，且发布结果可复查。

## 推荐执行顺序

1. 先补齐各页面状态和响应式体验。
2. 再完成 PWA 能力和 Cloudflare 发布流程。
3. 最后补监控、回退方案和上线验收。

## 完成标准

- 应用可稳定部署到 Cloudflare。
- 主要页面具备生产级的异常与空状态处理。
- PWA 安装和离线行为清晰可验证。
- 发布、监控和回退都有明确操作文档。
