# Phase 2 Plan

基于当前 `upload`、`invoices`、`suppliers` 页面仍为 shell 状态整理。

## 当前状态

- `src/routes/upload.tsx` 已明确下一步要做 textarea 解析、Zod 校验、可编辑预览和保存流程。
- `src/routes/invoices/index.tsx` 与 `src/routes/invoices/$invoiceId.tsx` 已具备页面框架，但仍使用静态假数据。
- `src/routes/suppliers/index.tsx` 已有供应商目录界面骨架，但尚未从 D1 读取真实数据。
- 数据 schema 已具备落库条件，说明 Phase 2 的核心是“导入与 CRUD 打通”。

## 本阶段目标

把 Gemini 发票 JSON 从“可展示样例”推进到“可校验、可修正、可保存、可查询”的完整业务闭环。

## 剩余任务

### 1. 定义导入数据契约

- 为粘贴的 JSON 建立 Zod schema，明确发票头部字段、明细行字段、数值格式与必填项。
- 增加标准化层，把西语字段、单位、金额和税率转换为内部统一结构。
- 设计分类匹配与兜底策略，避免导入时因为分类名称不一致而中断。
- 完成标准：同一份输入在前端预览和后端落库时使用同一份规范化结果。

### 2. 实现上传与预览流程

- 将 `upload` 页面从静态 `<pre>` 改为真实 textarea 输入。
- 增加“解析预览”动作，展示字段级校验错误与结构化预览结果。
- 支持发票头部与明细行的内联修正，避免用户必须回到 JSON 原文里修改。
- 完成标准：用户可以在页面内完成“粘贴 -> 校验 -> 修正 -> 准备保存”。

### 3. 打通发票保存流程

- 新增服务端写入逻辑，按事务保存 supplier、invoice、invoice_items。
- 供应商采用“已存在则复用，不存在则自动创建”的策略。
- 保存原始 JSON 到 `invoices.rawJson`，便于后续审计和回溯。
- 定义保存后的状态策略，例如默认 `draft` 后人工确认，或直接 `verified`。
- 完成标准：成功保存后可返回新发票 ID，并在列表页可见。

### 4. 落地发票列表与详情页

- 列表页从 D1 拉取真实发票，支持按日期排序、状态过滤、关键字搜索。
- 详情页根据 `invoiceId` 加载发票头部和明细行，不再显示静态数据。
- 增加编辑与删除能力，删除时触发 `invoice_items` 级联清理。
- 完成标准：用户可以查看、修改并删除已保存发票。

### 5. 让供应商目录由数据驱动

- 供应商页面改为从 D1 查询真实供应商列表。
- 支持维护联系人与备注字段，为后续采购谈判和履约记录做准备。
- 增加基础汇总字段，例如发票数、最近采购日期、累计金额。
- 完成标准：供应商页不依赖假数据，且能反映导入后的真实业务状态。

### 6. 补充验证与回归测试

- 为导入 schema、标准化逻辑、保存事务补单元测试。
- 为上传主路径补集成测试，覆盖合法输入、字段缺失、数值异常等场景。
- 为发票删除和供应商自动创建补回归测试，防止数据污染。
- 完成标准：Phase 2 的核心闭环具备自动化回归保护。

## 推荐执行顺序

1. 先定义导入 schema 和标准化逻辑。
2. 再完成上传页的解析、错误展示和可编辑预览。
3. 然后打通服务端保存与发票列表/详情查询。
4. 最后把供应商目录改为真实数据，并补测试收尾。

## 完成标准

- 用户可从 `/upload` 完成粘贴、校验、修正和保存。
- `/invoices/` 与 `/invoices/$invoiceId` 使用真实 D1 数据。
- `/suppliers/` 能展示并维护真实供应商记录。
- 导入与 CRUD 主路径有自动化测试覆盖。
