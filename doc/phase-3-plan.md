# Phase 3 Plan

基于当前 `analytics`、`compare` 与 dashboard 已有展示骨架，但查询逻辑尚未落地的状态整理。

## 当前状态

- `src/routes/analytics.tsx` 已明确需要产品搜索、月度趋势、平均价、最高价、最低价、采购数量和样本数。
- `src/routes/compare.tsx` 已明确需要“同产品各供应商最新价格”的 SQL 排名逻辑。
- 首页已预留 dashboard 指标位，但当前仍是静态说明文案。
- Phase 3 的前置条件是 Phase 2 已经把发票与明细稳定写入 D1。

## 本阶段目标

把已落库的采购明细转化为可决策的价格趋势和供应商对比能力，让应用从录入工具升级为分析工具。

## 剩余任务

### 1. 落地 dashboard 核心指标

- 把首页中的静态指标改为真实查询结果。
- 优先实现总采购额、活跃供应商数、最近导入发票数、最近周期采购品类数等基础运营指标。
- 为空状态准备合理回退文案，避免新库首次打开时显示错误信息。
- 完成标准：首页展示的是当前数据库真实状态，而不是固定数字。

### 2. 实现产品搜索与自动补全

- 以 `invoice_items.productName` 为基础实现搜索建议。
- 处理同名商品的规格差异和命名漂移，必要时增加最小标准化策略。
- 限制搜索范围与分页策略，避免全表扫描拖慢交互。
- 完成标准：用户能快速定位单个商品并进入分析视图。

### 3. 实现价格趋势查询

- 按月聚合商品价格，输出 `AVG(unit_price)`、`MIN(unit_price)`、`MAX(unit_price)`、`SUM(quantity)`、`COUNT(*)`。
- 支持时间窗口过滤，例如近 3 个月、近 6 个月、近 12 个月。
- 明确数量单位冲突的处理方式，避免把 `kg` 和 `ud` 的商品直接混算。
- 完成标准：分析页可以展示可解释的月度趋势结果。

### 4. 实现供应商比价矩阵

- 以“每个商品、每个供应商的最新价格”为基础构建查询。
- 使用窗口函数实现最新样本筛选和价格排名，优先支持 `ROW_NUMBER()` 与 `RANK()` 逻辑。
- 增加产品过滤和结果排序，让页面能承载真实数据量。
- 完成标准：比价页能基于真实发票明细给出当前最优供应商排序。

### 5. 做查询性能与数据一致性治理

- 复核现有索引是否足以支撑趋势查询和比价查询，必要时补充组合索引。
- 为搜索、时间过滤和最新价格查询建立 explain/checklist，避免后期数据量增长后明显退化。
- 明确脏数据处理规则，例如缺失单位、重复商品名、异常单价。
- 完成标准：核心查询在目标数据规模下可稳定响应。

### 6. 补齐分析层测试

- 为 SQL 聚合与排名逻辑补查询级测试。
- 为空状态、单供应商样本、跨月无数据等边界场景补 UI 测试。
- 为趋势和比价结果的关键数值补快照或断言，减少后续回归风险。
- 完成标准：分析结果不仅能显示，还能被自动化验证。

## 推荐执行顺序

1. 先完成 dashboard 指标和产品搜索。
2. 再实现趋势查询。
3. 然后实现比价矩阵。
4. 最后做索引优化、边界处理和测试补强。

## 完成标准

- 首页、分析页、比价页全部依赖真实 D1 数据。
- 价格趋势和供应商排序可解释、可过滤、可验证。
- 核心查询具备基本性能保障和自动化测试覆盖。
