# Phase 3 Plan

基于当前 `analytics`、`compare` 与 dashboard 已有展示骨架，但查询逻辑尚未落地的状态整理。

## 当前状态

- `src/routes/analytics.tsx` 已明确需要产品搜索、月度趋势、平均价、最高价、最低价、采购数量和样本数。
- `src/routes/compare.tsx` 已明确需要“同产品各供应商最新价格”的 SQL 排名逻辑。
- 首页已预留 dashboard 指标位，但当前仍是静态说明文案。
- Phase 3 的前置条件是 Phase 2 已经把发票与明细稳定写入 D1。

## 本阶段目标

把已落库的采购明细转化为可决策的价格趋势和供应商对比能力，让应用从录入工具升级为分析工具。

## 完成状态

### 已完成

- [x] 把首页中的静态指标改为真实查询结果。
- [x] 实现总采购额、活跃供应商数、最近导入发票数、最近周期采购品类数等基础运营指标。
- [x] 为首页空状态加入回退文案，避免新库首次打开时显示错误信息。
- [x] 完成标准：首页展示当前数据库真实状态，而不是固定数字。

### 2. 实现产品搜索与自动补全

- [x] 以 `invoice_items.productName` 为基础实现搜索建议。

- [x] 通过标准化字段、索引和结果限制约束搜索范围，避免拖慢交互。

### 3. 实现价格趋势查询

- [x] 完成标准：比价页能基于真实发票明细给出当前最优供应商排序。

### 6. 补齐分析层测试

- [x] 为 SQL 聚合与排名逻辑补查询级测试。
- [x] 为空状态、多单位冲突等边界场景补 UI 测试。
- [x] 为趋势和比价结果的关键数值补断言，减少后续回归风险。
- [x] 完成标准：分析结果不仅能显示，还能被自动化验证。

## 推荐执行顺序

1. 先完成 dashboard 指标和产品搜索。
2. 再实现趋势查询。
3. 然后实现比价矩阵。
4. 最后做索引优化、边界处理和测试补强。

## 完成标准

- 首页、分析页、比价页全部依赖真实 D1 数据。
- 价格趋势和供应商排序可解释、可过滤、可验证。
- 核心查询具备基本性能保障和自动化测试覆盖。
